**核心论点：主动软件工程能力必须同时证明“发现的是缺陷”和“修改没有制造回归”；没有 Issue 的任务中，生成一个看似合理的补丁不构成成功。**

## 既有基准省略了最昂贵的一段工作

多数 Coding Agent 基准提供清晰 Issue、预期行为和单个目标缺陷。真实维护通常从弱信号开始：偶发日志、失败测试、类型不一致、性能异常或依赖升级后的行为变化。工程师需要先判断现象是否成立、影响范围多大、哪条假设值得验证，才进入写补丁阶段。

Active-SWE 将评测起点前移到没有 Issue 报告的代码库，包含 1,663 个任务、6 类缺陷和 8 种语言，并覆盖已记录缺陷、多缺陷修复与潜在缺陷发现。实验显示，现有先进 Coding Agent 在定位、批量修复和提出有效新缺陷方面仍然困难。这一结论把“会修”与“会发现”明确拆开。

## 主动发现的证据链

一个可审计的发现应经过：

```text
异常信号
  → 可复现条件
  → 最小失败用例
  → 根因假设
  → 影响面搜索
  → 候选补丁
  → 独立回归验证
```

若缺少最小失败用例，Agent 容易把风格偏好当成 Bug；若缺少影响面搜索，局部修复可能破坏其他调用者；若发现者同时拥有最终裁决权，系统容易用自己生成的测试证明自己正确。

## 从单 Agent 循环到角色分离

工程上可拆成 Explorer、Fixer 和 Verifier。Explorer 只读地扫描代码、测试、静态分析与历史变更，输出带证据的缺陷候选；Fixer 在明确任务封套内修改；Verifier 使用独立上下文重现旧失败、运行新增测试并检查回归。角色分离的目的不是增加对话轮数，而是避免同一假设同时控制发现、修改与验收。

候选缺陷还需要置信度、严重度、受影响版本、复现成本和证据位置。低置信度项进入人工分诊，高置信度且可自动验证的项才进入修复队列。生产仓库默认从只读扫描开始，写权限按任务逐次授予。

## 如何衡量主动能力

指标至少包含缺陷级 precision/recall、可复现率、修复率、回归率、多缺陷覆盖率与每个有效发现的成本。仅统计提交数量会奖励噪声；仅统计测试通过会遗漏无测试覆盖的误改。对于“潜在缺陷”，需要独立专家或维护者确认，并保留未确认类别，避免强行二元化。

## 反例、局限与适用边界

某些仓库缺少可执行测试或构建环境，主动发现只能形成假设而非结论。静态规则在一种语言有效，换到另一种语言可能产生大量误报。基准中的缺陷分布也不等于生产缺陷分布。安全敏感、遗留或强合规代码库适合先提供诊断报告，不应默认自动提交修改。

## 在七篇中的位置

Active-SWE 为 Self-Evolving 闭环提供新失败，但 GDPevo 要求这些经验能迁移；Agent Runtime 管理长扫描、资源预算和恢复；PIMiner 约束仓库内的不可信指令；SuperScout 负责构建可验证的仓库证据；MCP Stateless 通过受治理工具暴露测试、搜索与提交能力。
