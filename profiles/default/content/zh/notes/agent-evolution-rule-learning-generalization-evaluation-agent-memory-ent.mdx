## 核心判断

Agent 自我改进最大的风险，不是不会优化，而是优化方向错误。

很多 Agent 优化流程实际上是在训练集上修补失败：某个任务失败 → 增加规则 → 重新测试 → 成功。

但这种提升可能只是记住了任务，而不是获得了可迁移能力。

GDPevo 关注的问题是：

> 如何判断一个 Agent 是否真正从经验中学习到了通用规律，而不是记住了历史案例？

这对于所有长期运行的 Agent 系统都重要，因为真实环境中的任务不会重复出现，而是不断组合新的约束。

---

## 背景问题：Task Success 不等于 Capability Growth

传统 Agent 优化通常关注：

```text
失败任务
  ↓
修改 Prompt / Memory / Tool
  ↓
重新运行
  ↓
成功
```

问题在于：成功只能证明这个任务被修复。

不能证明 Agent 学会了背后的规则。

例如：

任务 A：退款失败。

原因：没有检查金额限制。

加入规则：

```
退款前检查金额限制
```

任务 A 成功。

但是任务 B：修改订单金额。

如果 Agent 再次忘记金额约束，说明它学习的是：

```
退款 → 检查金额
```

而不是：

```
所有资金相关操作 → 必须执行约束验证
```

前者是记忆，后者才是能力。

---

## 核心思想：从任务优化转向规则泛化

GDPevo 的关键思想是：

不要只评估 Agent 是否完成任务，而要评估 Agent 是否掌握任务背后的规则结构。

企业任务通常不是孤立的。

一个业务动作往往由多个规则组合：

```
退款
 ├── 用户权限
 ├── 金额限制
 ├── 订单状态
 └── 财务记录
```

真正的问题不是：

“Agent 会不会退款？”

而是：

“Agent 是否理解资金操作需要哪些约束？”

---

## 关键方法：Rule Composition

GDPevo 的核心价值在于引入规则组合思维。

任务可以拆解为：

```
Task
 ↓
Atomic Rules
 ↓
Rule Combination
 ↓
New Task
```

训练阶段：

Agent 看到某些规则组合。

测试阶段：

重新组合规则，生成未见任务。

如果 Agent 仍然正确，说明它学习到了规则，而不是记住任务。

## 对 Agent Memory 的启发

这是最值得工程实践的一点。

很多 Memory 设计保存：

```
上次任务怎么解决
```

例如：

```json
{
 "task":"refund order",
 "solution":"call refund API"
}
```

这种 Memory 很难迁移。

更好的 Memory 应保存：

```
什么条件触发什么规则
```

例如：

```yaml
rule:
  external_state_mutation_requires_validation

trigger:
  operation_type = financial_change

constraints:
  - permission_check
  - amount_validation
  - audit_record
```

这种 Memory 才能跨任务复用。

## Agent Evolution 的正确闭环

结合 Self-Evolving Agent，可以形成：

```
Production Failure
        ↓
Failure Pattern
        ↓
Rule Extraction
        ↓
Transfer Evaluation
        ↓
Agent Update
```

关键步骤不是修复失败。

而是从失败中抽象规则。

例如：

低质量优化：

```
增加 20 条 Prompt
```

高质量优化：

```
所有外部写操作必须经过授权验证
```

后者可以作用于整个系统。

## 工程实现方案

### 1. Rule Store

建立独立规则层：

```
agent-rules
 ├── security
 ├── business
 ├── workflow
 └── domain
```

规则包含：

- 触发条件
- 适用范围
- 执行动作
- 验证方式
- 来源

---

### 2. Failure Pattern Extraction

不要记录：

```
Agent failed
```

而记录：

```
failure_type:
missing_validation

pattern:
external mutation without authorization

affected_tasks:
finance, crm, deployment
```

---

### 3. 三层 Evaluation

真正有效的 Agent Evolution 需要：

### Seen Task

验证旧问题是否修复。

### Transfer Task

验证规则是否迁移到相似但不同任务。

### Composition Task

验证多个规则组合时是否仍然正确。

第三层最接近真实企业环境。

## 对 Agent 系统设计的影响

未来 Agent Platform 不应该只有：

```
Prompt Store
```

而应该包含：

```
Prompt
Skills
Tools
Rules
Memory
Evaluation
Failure Patterns
```

其中 Rules 是连接经验和能力的关键层。

---

## 局限性

需要注意：

GDPevo 并不证明 Agent 已经具备类似人类的理解能力。

它证明的是：

在可结构化任务环境中，通过规则抽象和组合测试，可以更准确衡量 Agent 是否获得迁移能力。

真实业务仍存在：

- 隐含规则
- 冲突规则
- 动态政策
- 人类经验

这些需要结合人工反馈、运行数据和持续评测解决。

---

## 最终沉淀

Agent Evolution 的核心不是：

```
更多数据
+
更多 Prompt
```

而是：

```
经验
 ↓
模式
 ↓
规则
 ↓
迁移验证
 ↓
能力
```

真正成熟的 Agent，不是记住更多答案，而是能够从经验中提炼可复用规律。
