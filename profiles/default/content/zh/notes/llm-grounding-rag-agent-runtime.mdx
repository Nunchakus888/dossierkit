> 一个危险的事实错误，往往不是从“无中生有”开始，而是从“半句话是真的”开始：模型拿到一个区域名、一栋大厦名和几段关于自提的无关知识，便顺手补齐了街道、门牌、楼层、营业时间与服务承诺。真正需要修复的，不是某个地址，而是系统允许模型把“应当去哪里查”误当成“已经查到了什么”。

## 摘要

本文复盘某电商客服 Agent 的一次生产事故：用户询问线下自提，系统却生成了完整但错误的门店地址、营业时间、取货规则和通知承诺。逐层核验运行时 Instructions、Background、检索结果、对话历史与工具调用后，我们确认：配置中只有部分地点线索；检索返回的是邻近主题但不支持答案的物流内容；模型没有访问官网，也没有命中能支持这些细节的知识。根因不是地址配置错误，而是模型把“官网信息为准”这一来源治理规则误认作事实证据，并把若干弱相关片段拼成了一条完整业务命题。

修复没有使用地址关键词、客户分支或事故专属样例，也没有增加第二个审查模型。我们将回答协议改造成一次模型调用内完成的“草稿—所需命题—直接证据—未决项—闸门—可发布分支”，再由运行时只发布结构化闸门选中的分支。模型负责语义判断，程序负责结构验证与失败关闭。最终事实矩阵 60/60、历史案例回放 28/28、语言矩阵 11/11、常规 Agent 回归 1312 通过；固定输入与内部审计预计增加约 850–1300 tokens/轮，但避免了串行 reviewer 常见的额外模型往返。

中心结论是：**生产级幻觉治理的关键，不是继续堆叠“不要编造”的规则，而是把证据充分性变成模型必须完成、运行时能够验证、上线后可以观测的发布协议。**

## 1. 一次“看起来很像真的”事故

用户的真实意图很普通：线上购买后，能否到门店自提？

Agent 的回答却异常完整：它给出了街道、门牌、楼层、房号、营业时间、自提政策，甚至承诺到货后会通知用户。完整性制造了可信感，也放大了伤害——用户并不会把它看成一次语言生成，而会把它当成商家的确定承诺。

排查时，我们把最终回答中的每个可验证命题拆开，并反向寻找来源：

| 回答命题 | Instructions | Background | RAG/工具 | 对话历史 | 结论 |
|---|---:|---:|---:|---:|---|
| 门店位于某区域、某大厦 | 部分相关 | 有部分线索 | 无直接支持 | 无 | 仅支持粗粒度位置 |
| 街道、门牌、楼层、房号 | 无 | 无 | 无 | 无 | 编造 |
| 营业时间 | 无 | 无 | 无 | 无 | 编造 |
| 支持该用户所述自提流程 | 无 | 无 | 返回的是其他物流/自提语境 | 无 | 错误归因 |
| 到货后一定通知 | 无 | 无 | 无 | 无 | 编造业务承诺 |

最关键的运行时信号是：模型把证据标成了“Instructions”。然而 Instructions 只说“基础信息以网站为准，不得擅自更改”，并未包含网站内容，更没有证明上述地址和服务政策。

这揭示了一类容易被忽视的语义错误：

- “官网是权威来源”是**来源治理规则**；
- “官网写明地址为 X”才是**事实证据**；
- 前者规定去哪儿验证，不能替代后者完成验证。

## 2. 根因：从局部真实到完整虚构

事故不是单点失败，而是一条可复现的错误链：

~~~mermaid
flowchart LR
    A[用户用上下文短句询问自提] --> B[检索召回邻近主题：物流、自提柜、其他服务]
    C[Background 只有区域与大厦等局部线索] --> D[模型追求完整、可执行的客服回答]
    B --> D
    A --> D
    D --> E[补齐地址细节、时间与服务承诺]
    F[Instructions: 以官网为准] --> G[被误当成已经取得的官网事实]
    G --> E
    E --> H[模型自报 evidence = instructions]
    H --> I[运行时相信标签并发布]
~~~

这里至少有四种机制叠加：

1. **命题补全倾向。** 用户需要一个可执行答案，模型便把“区域 + 大厦”补成邮寄级地址。
2. **检索相关性替代蕴含关系。** “自提”主题相关，不等于“该商家支持该自提流程”。
3. **关系拼接。** 不同片段分别出现主体、地点或服务概念，模型据此创造了来源从未明确表达的关系。
4. **自报证据不可验证。** 系统记录了“evidence: instructions”，却没有检查证据是否真的支持完整命题。

因此，这不是“知识库里有一个错地址”，也不是输入字符异常；它是典型的**部分事实 + 干扰检索 + 来源规则误读**所诱发的生成型幻觉。

## 3. 为什么直觉修法不够

### 3.1 为地址、卡号、品牌关系分别写禁令

这会迅速演变成事故词典：今天禁止补门牌，明天禁止补银行卡，后天禁止补售后承诺。它既漏掉未知类型，也让 Prompt 被个案挤占。生产规则应描述“什么事实可以发布”，而不是枚举“哪些词不能编”。

### 3.2 再写一遍“不得幻觉”

普通自然语言禁令仍由同一个概率模型解释。前一次类似事故已证明，只有原则而没有证据协议时，模型仍可能把“有参考线索”解释成“足以回答”。

### 3.3 只升级模型

将模型升级到更强版本、使用低推理强度后，在关闭最终事实闸门的消融测试中只通过 3/9。更强模型改善表达和推理上限，却不会自动建立服务端可执行的发布边界。

### 3.4 增加第二个 reviewer

独立 reviewer 有价值，但会增加一次串行模型调用，带来明显延迟与成本；如果 reviewer 看到的仍是同一批模糊材料，它也可能复述第一次判断。对于高吞吐客服链路，先把证据审计纳入同一次调用，具有更好的成本—收益比。

## 4. 修复：单调用 Evidence Gate

新的回答协议要求模型在一次调用内完成六个逻辑阶段：

~~~mermaid
flowchart LR
    A[User + Instructions + Background + RAG/Tool] --> B[Draft]
    B --> C[Needed: 回答所需的完整业务命题]
    C --> D[Supported: 可逐字定位的直接证据]
    D --> E[Unresolved: 缺失或冲突项]
    E --> F{use_limitation_only}
    F -- false --> G[content]
    F -- true --> H[limitation]
    G --> I[运行时只发布选中分支]
    H --> I
~~~

结构化响应的核心字段及职责如下：

| 字段 | 模型职责 | 运行时职责 |
|---|---|---|
| response_language | 依据当前对话与配置确定回答语言 | 校验枚举/格式 |
| draft | 先形成候选回答，暴露需要验证的主张 | 永不直接发布 |
| evidence | 为回答所需命题给出紧凑的直接来源片段，并记录未决项 | 校验结构完整性 |
| use_limitation_only | 在证据不足时打开限制闸门 | 决定唯一可发布分支 |
| limitation | 简洁说明当前无法确认什么 | 闸门打开时发布 |
| content | 证据充足时的正常回答 | 闸门关闭时发布 |

这不是让程序用关键词判断真假。**语义上的“是否支持”仍由 LLM 完成；程序只做它擅长的事：验证协议、选择分支、拒绝畸形输出。** 如果结构解析失败，系统重试或失败关闭，绝不从未审计草稿中恢复答案。

### 4.1 完整命题原则

事实证据必须覆盖一个业务命题的关键槽位：主体、关系、客体及限定条件。可形式化为：

例如，“某大厦位于中环”不能支持“该品牌门店位于该大厦某层某室”；“知识库描述一种自提服务”不能支持“该商家向当前用户提供这种服务”。多个来源片段也不得被拼接成它们从未共同表达的业务关系。

### 4.2 证据不足时的行为

若关键命题无法从可信来源直接得到支持，模型只能：

1. 在可用时查询一次知识；
2. 仍无证据则明确、简洁地说明无法确认；
3. 不补充未经支持的建议、替代流程或下一步承诺。

限制回答不是失败，而是证据边界在用户界面的显式呈现。与此同时，测试必须包含充足证据下的正向回答，防止系统退化为“安全但无用”的一律拒答器。

## 5. 验证：安全性不能只测事故原句

测试矩阵刻意避免只复现一个地址。它覆盖了地址、支付账号、品牌关系、业务承诺、上下文不足、Instructions 缺失、知识库缺失/无关/错误，以及证据充分时应正常回答的正向案例；同时回归语言遵守、会话流程和常规工具行为。

| 验证层 | 结果 | 说明 |
|---|---:|---|
| 仅升级模型、关闭最终事实 Gate | 3/9 | 证明模型升级不是充分条件 |
| 最终事实场景矩阵 | 60/60 | 同时含拒答与正向回答 |
| 历史案例回放 | 28/28 | 验证既有问题没有回潮 |
| 多语言矩阵 | 11/11 | 中文、英文、西语、切换、限制与正常回答 |
| 语言优先级重复测试 | 20/20 | 检查概率性波动 |
| 定向单元/集成测试 | 235/235 | 覆盖协议解析与分支选择 |
| Agent 非 E2E 回归 | 1312 通过，4 跳过 | 检查常规能力 |
| 预发完整 E2E | 37/37 场景，49/49 轮 | 全部请求被接受，内容审计全通过 |

需要诚实说明：3/9 的消融集与 60/60 的最终扩展矩阵规模不同，因此它证明“升级模型仍存在明显失败”，但不能被解读为严格受控的效应量比较。论文级结论仍需在相同数据集、相同采样参数和多次重复下对照。

## 6. 成本、延迟与运行稳定性

该方案没有增加第二次模型调用。预计每轮增加：

- 固定 Prompt：约 500–700 输入 tokens；
- 私有草稿、证据与 Gate：约 150–300 输出 tokens；
- 合计：约 850–1300 tokens，约为预发平均单轮用量的 6%–10%。

预发 49 轮样本中，端到端延迟 p50 为 10.42 秒、p95 为 17.67 秒、最大 18.20 秒；Pod 无重启、无 5xx。上线初始观察窗口中，已完成对话 p50 为 7.17 秒、p95 为 16.30 秒、最大 18.07 秒。它不能证明所有流量形态下都无回归，但说明在已观测窗口内，安全协议没有引入第二调用式的阶跃延迟。

## 7. 与现有研究的关系

该设计与已有事实性方法共享“先生成、再检查”的思想，但工程约束不同：

| 方法 | 主要机制 | 与本文方案的区别 |
|---|---|---|
| [RAG](https://arxiv.org/abs/2005.11401) | 参数记忆结合外部检索 | RAG 提供材料，不保证材料蕴含最终命题 |
| [RARR](https://arxiv.org/abs/2210.08726) | 外部研究、归因并修订输出 | 通常包含额外检索与修订阶段 |
| [Self-Refine](https://arxiv.org/abs/2303.17651) | 同一模型多轮反馈与改写 | 依赖迭代调用；本文把审计压入一次结构化调用 |
| [Chain-of-Verification](https://arxiv.org/abs/2309.11495) | 草稿、验证问题、独立作答、最终回答 | 验证链更显式但通常是多阶段；本文强调低延迟运行时门控 |
| [Self-RAG](https://arxiv.org/abs/2310.11511) | 训练反思 token，自适应检索与生成 | 需要训练机制；本文是模型无关的推理时协议 |
| [FActScore](https://arxiv.org/abs/2305.14251) / [SAFE](https://arxiv.org/abs/2403.18802) | 原子事实分解与事实性评测 | 主要解决评估；本文把类似分解思想放入在线发布路径 |
| [ALCE](https://arxiv.org/abs/2305.14627) | 评价长文本的引用正确性与完整性 | 说明“有引用”不等于“每项主张都被引用支持” |

本文当前最有价值的差异，是把事实审计设计成**单调用、结构化、失败关闭、可兼容现有 Agent 运行时**的发布协议，并在真实的 RAG 干扰场景中同时验证拒答质量、正向可用性、语言遵守和系统回归。它是一项有研究潜力的工程设计，而不是已经证明优于上述方法的新算法。

## 8. 能否发布 arXiv？

### 结论

**现在适合公开为高质量工程案例或技术报告，但还不足以直接作为有说服力的独立 arXiv 论文。** arXiv 要求稿件具有学术主题相关性、可审阅的科学贡献并达到学术规范；新作者或首次进入某分类还可能需要 endorsement，稿件也会经过 moderation。参见 arXiv 的[提交规范](https://info.arxiv.org/help/submit/index.html)与[作者认证说明](https://info.arxiv.org/help/endorsement.html)。

当前证据的优势是真实生产问题、清晰因果链、完整实现和多层回归；短板是样本仍以内部分层矩阵为主，缺乏统一公开基准、多模型重复实验、人工标注一致性和可复现实验包。仅把一次修复扩写成论文，容易被审稿人评价为“有效的 Prompt engineering，但新颖性和外部有效性不足”。

### 变成论文需要补齐的证据

建议把研究问题明确为：

> 在不增加第二次 LLM 调用的约束下，结构化证据闸门能否比普通 RAG Prompt、模型升级和独立 reviewer 更好地降低不受支持的业务事实，同时保持回答效用、语言遵守与可接受延迟？

最小论文包应包括：

1. **公开或可公开的去标识数据集。** 300–1000 个案例，覆盖多行业、多语言、缺失证据、冲突证据、干扰检索与正向充分证据；真实客户内容必须脱敏，最好以可复现的合成变体补足。
2. **严格对照。** Plain RAG、仅加“不得编造”、仅升级模型、结构化 JSON、独立 reviewer、CoVe/RARR 风格多阶段验证，以及本文单调用 Gate。
3. **多模型实验。** 至少三个模型家族，每个案例重复 5–10 次，报告置信区间或配对 bootstrap，避免把一次采样结果当成稳定能力。
4. **兼顾安全与效用的指标。** Unsupported Claim Rate、证据蕴含精确率/召回率、过度拒答率、任务完成率、语言遵守率、端到端 p50/p95、token 与成本。
5. **完整消融。** 分别移除 Draft、Needed、Supported、Unresolved、Gate 和运行时 parser，确认收益来自哪个组件，而不是字段数量或更长 Prompt。
6. **可靠人工评审。** 双人或多人盲标，给出标注指南、分歧处理与一致性指标。
7. **可复现实验资产。** 发布去标识 Prompt、schema、评测脚本、合成数据和隐私声明；不能公开的生产数据只用于外部效度补充。

若这些条件完成，论文可以主投 [cs.CL](https://arxiv.org/category_taxonomy)（自然语言处理与事实性生成），并在强调生产 Agent 测试、运行时契约和可靠性工程时交叉列入 cs.SE。cs.AI 不是最优主分类，因为该工作核心仍是语言模型生成与证据对齐。

## 9. 可迁移的实践原则

1. **证据必须是可检查的对象，不是模型自报的标签。**
2. **检索相关性不等于命题蕴含；“附近的真话”仍可能导向核心假话。**
3. **规则描述可信发布条件，不枚举事故关键词。**
4. **语义判断交给模型，协议验证和分支选择交给程序。**
5. **任何未经审计的恢复路径都会成为旁路；结构失败应关闭发布。**
6. **安全测试必须同时包含正向用例、语言用例和常规业务回归。**
7. **模型升级提高上限，运行时契约决定底线。**

这次事故最值得留下的，不是一个“禁止编造地址”的补丁，而是一条更普遍的设计准则：**当生成模型参与真实业务决策时，答案不应因为“听起来合理”而获得发布资格，只应因为“关键命题已被本轮可信证据完整支持”而获得发布资格。**
