**核心论点：只有当一次改进能通过隔离的回归测试与迁移测试，并且能够定位到明确的 Harness 变更时，Coding Agent 才算获得了可复用能力；同题重试成功不能证明“进化”。**

## 为什么这个问题重要

软件工程给 Agent 提供了少见的闭环：仓库状态可复现，修改可形成差异，测试可执行，失败轨迹可回放。它因此天然适合持续学习，也天然容易制造假进步。一个 Agent 可能通过增加提示词、记住某个补丁或放宽完成条件，让单个任务从失败变成通过；与此同时，其他仓库、相邻任务甚至原有能力都可能退化。

《Self-Evolving Coding Agents》将这一领域的演进对象归纳为框架、记忆、技能、工具、模型与协作结构，并强调演进发生的时机以及软件特有证据。这个视角把“升级模型”改写为更具体的问题：系统究竟修改了哪一层，依据什么反馈，凭什么允许它进入生产。

## 从失败轨迹到候选变更

有效的进化链应当是：

```text
可复现失败
  → 轨迹与环境快照
  → 责任层归因
  → 单一、可回滚的候选变更
  → 修复集 + 回归集 + 迁移集
  → 受控发布
```

责任层至少要区分模型推理、上下文选择、工具接口、执行环境、终止条件和验证器。若根因是测试命令被错误解析，增加“更认真检查代码”的提示词不会修复系统；若根因是上下文缺失，更换更大的模型也可能只是昂贵地重复失败。归因的价值在于缩小变更面，使结果能够被解释、复现与回滚。

## 评测必须把“修好”与“学会”分开

可采用四个门：

1. **Reproduction**：旧版本能稳定复现失败，排除随机波动。
2. **Repair**：候选版本修复目标任务。
3. **Regression**：原有能力、成本与安全约束没有显著恶化。
4. **Transfer**：相同原则在未见仓库或新约束组合中仍然成立。

第四个门决定改进是案例记忆还是能力增长。它与 GDPevo 的规则杂交互补：前者提供 Coding Agent 的演进对象与反馈来源，后者提供更严格的迁移测量方法。

## 工程落地：把 Harness 当成可发布软件

每次演进应形成版本化制品：变更说明、基线版本、失败簇、评测清单、成本差异、权限变化与回滚点。提议变更的组件不能单独决定晋级；验证环境需要与优化过程隔离，保留冻结测试集，并对新增工具权限进行独立审批。

生产侧应持续采集结构化轨迹，但不能把所有成功路径直接写入长期记忆。轨迹先进入失败聚类和候选规则层，经多次证据与迁移评测后，才晋升为 Skill、Policy 或 Runtime 配置。

## 反例、局限与适用边界

测试通过不等于业务正确：测试本身可能缺失关键约束，模型也可能利用评测漏洞。仓库演进还会导致基准过时；旧任务上的稳定收益未必能迁移到新依赖、新语言或新工具链。对于安全、财务和生产发布，自动演进更适合提出候选与运行评测，不应自行扩大权限或绕过人工批准。
