## 核心判断
Agent 自我改进最大的风险是：修复成功并不代表真正变强。

Agent 可能只是记住了某个任务模式，而不是理解背后的通用规则。

真正的进化应该表现为：从过去经验中提炼可迁移规律，在未知任务组合中继续有效。

## 背景问题
传统优化关注：

任务失败 → 修改 Agent → 原任务成功。

但如果 Agent 只针对具体案例优化，就会产生 Task Memorization，而不是 Rule Generalization。

例如：

退款任务失败，因为没有检查金额限制。

低质量修复：退款前检查金额。

高质量抽象：所有涉及资金变更的操作都需要业务约束验证。

## 核心思想
GDPevo 的关键不是增加任务数量，而是验证 Agent 是否学习到了任务背后的规则结构。

从：

Task → Solution

转向：

Task → Rules → Rule Combination → New Task

## Rule Composition
真实企业任务不是孤立流程，而是多个规则组合。

例如退款包含：

- 订单状态
- 用户权限
- 金额限制
- 风控规则
- 财务记录

Agent 的能力应该体现为理解这些约束关系，而不是记住某个操作路径。

## 对 Memory 的启发
低质量 Memory 保存：

“上次退款调用了 refund API。”

高质量 Memory 保存：

“涉及资金变更时，需要权限检查、额度验证和审计记录。”

Memory 的价值在于保存可迁移规则，而不是历史轨迹。

## Agent Evolution 正确闭环
Failure
↓
Pattern Extraction
↓
Rule Generation
↓
Transfer Evaluation
↓
Update Agent

关键步骤是从大量失败中抽象共同规律。

## Eval 设计
需要三层：

1. Seen Task：验证旧问题修复。
2. Transfer Task：验证规则迁移。
3. Composition Task：验证多规则组合。

## 工程落地
建立 Rule Store：

- rule_id
- description
- trigger
- action
- scope
- validation cases

运行时：

Agent Trace
↓
Failure Cluster
↓
Common Pattern
↓
Rule Candidate
↓
Evaluation
↓
Activate

## 最终沉淀
Agent Evolution 不是：

更多数据 + 更多 Prompt = 更强 Agent。

而是：

经验 → 抽象规则 → 验证迁移 → 形成能力。

未来 Agent 系统的重要能力，是把运行经验转化为可验证规则的机制。
