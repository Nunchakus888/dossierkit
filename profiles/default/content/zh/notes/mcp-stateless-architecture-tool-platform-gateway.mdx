**核心论点：Stateless MCP 的价值是把协议会话状态移出工具服务，使每次请求可独立鉴权、路由和扩缩容；任务状态、记忆、审批与恢复仍必须由 Agent Runtime 或外部状态层显式管理。**

## 2026-07-28 版本改变了什么

新版 Streamable HTTP 移除了协议级 Session 与独立 GET 流。客户端把每个 JSON-RPC 请求作为新的 HTTP POST 发送到单一 MCP Endpoint；协议版本、客户端信息与能力等元数据随请求携带。服务端可以返回单个 JSON 对象，或只服务于该请求的 SSE 流。

这使负载均衡器无需 Session Affinity，失败实例也不会带走隐藏在内存中的协议状态。不同区域和不同版本的工具服务更容易水平扩展，Gateway 也能通过标准请求元数据完成路由与观测。

## 状态应当放在哪里

无状态指服务端无需记住前一个协议请求，并不禁止有状态业务：

```text
Agent Runtime
  ├─ Task / Memory / Approval / Budget / Recovery
  └─ Tool Call + State Reference
                 ↓
MCP Gateway
  ├─ Identity / Policy / Discovery / Routing / Trace
  └─ Stateless MCP Server
                 ↓
       Domain System of Record
```

订单、文件或部署状态仍保存在权威业务系统；Runtime 保存任务进度与审批；请求只携带完成本次工具调用所需的参数和状态引用。边界清楚后，MCP Server 不再同时扮演工作流引擎、记忆库和权限中心。

## Gateway 为什么成为能力平台

当工具数量从几十增长到数千，客户端直连每个 Server 会带来协议版本、身份、网络和可见性碎片。云端工具访问研究提出在数据面引入 Gateway，集中处理旧服务适配、MCP 变体、访问控制、工具推荐与路由。

生产 Gateway 至少需要：工具发现与版本、租户身份、参数级授权、风险与副作用标签、限流、成本计量、审计回执和渐进发布。工具描述也不能只有 name 与 schema；Runtime 还需要知道该调用是否写数据、是否可重试、是否需要批准以及可靠性 SLO。

## Stateless 带来的代价

无协议 Session 意味着服务端不能依赖长期连接任意向客户端发起请求。新版通过请求内的多轮往返机制处理 sampling、elicitation 等交互，长生命周期变更通知则使用显式订阅流。旧客户端与新服务端之间还存在版本协商与兼容成本。

因此，迁移不能只是删除 Session ID。原先藏在 Session 中的身份、能力协商、订阅、取消和恢复信息必须有新的明确归属；否则系统只是把隐式状态变成丢失状态。

## 工程落地顺序

先清点 Session 中实际保存的字段，区分任务状态、协议元数据和业务状态。将任务状态迁到 Runtime，将业务状态迁到 System of Record，将每次授权所需身份放入可验证请求。随后实现幂等键、超时、重试、版本协商和统一追踪，再通过 Gateway 做灰度流量与旧协议适配。

## 反例、局限与适用边界

本地 stdio、强双向交互或高频服务端通知可能更适合有状态连接。无状态请求会重复携带元数据，也可能增加延迟。Gateway 集中治理同时形成关键依赖，需要多区域容错和策略版本控制。协议升级解决连接语义，不会自动解决工具质量、业务幂等或 Agent 授权。

## 在七篇中的位置

MCP Stateless 是七篇的能力边界：Self-Evolving 与 GDPevo 管改进和评测，Agent Runtime 管任务状态，PIMiner 定义每次调用的安全门，Active-SWE 与 SuperScout 通过工具完成搜索和验证；MCP 只负责把这些能力以可治理协议暴露出来。
