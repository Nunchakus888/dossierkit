> 论文：*AREX: Towards a Recursively Self-Improving Agent for Deep Research*  
> arXiv: 2607.21461，2026-07-23  
> 原文：https://arxiv.org/abs/2607.21461  
> 模型：https://huggingface.co/collections/BAAI/arex

## 先澄清“递归自我改进”

AREX 所说的 Recursive Self-Improvement，不是 Agent 自动修改自己的模型、代码或 Harness，也不是无限开放式自我进化。

它实现的是一个**有轮次上限的推理时研究循环**：

```text
搜索并生成暂定答案
→ 按约束逐项验证
→ 保留已证实部分
→ 找出未解决部分
→ 将未解决部分改写成下一轮研究目标
→ Refine、Restart 或结束
```

因此，更准确的工程理解是：

> **AREX 是一个“验证驱动的研究状态迭代器”，不是通用意义上的自主自我进化系统。**

这一点很重要，因为它决定了我们可以在不训练新模型的情况下，先把它的大部分思想落到 Agent Harness 中。

## 核心洞察：发现难，验证相对容易

深度研究任务通常要求答案同时满足多个条件。例如寻找一个产品，可能同时要求：

- 某时间后发布；
- 支持某项协议；
- 可私有部署；
- 有官方定价；
- 来源必须是一手资料。

直接搜索一个同时满足所有条件的答案，搜索空间很大。但当一个候选已经出现后，逐项验证它是否满足条件通常更容易。

AREX 把这种现象称为 **discovery–verification asymmetry**：

```text
发现联合满足所有约束的候选：困难
验证一个候选是否满足某条约束：相对容易
```

普通 Research Agent 往往只是延长同一条搜索轨迹。早期错误会被不断继承，已经否定的方向可能被重复探索，部分满足条件的候选也可能被过早接受。

AREX 的关键变化是：**验证不再只是最终过滤器，而成为研究轮次之间的状态转换器。**

## 双循环结构

### 内层：Research Loop

内层负责完成当前研究目标：

```text
分析当前目标
→ search / visit
→ 获取和比较证据
→ 更新候选与判断
→ 必要时调用 update_context
→ finish 输出暂定答案、证据和置信度
```

第一轮的研究目标来自原始问题；后续轮次的目标由外层生成，例如：

- 验证某条未支持的条件；
- 解决来源之间的冲突；
- 检查时间有效性；
- 当前候选失效后寻找替代项。

### 外层：Self-Improvement Loop

外层收到结构化结果后做三路判断：

```text
Accept  ：证据充分，结束
Refine  ：当前轨迹有有效进展，只补未解决部分
Restart ：当前轨迹噪声过大或方向错误，从原问题重启
```

Refine 和普通“再搜一次”的区别在于：

- 保留已验证证据；
- 保留已否定候选；
- 明确剩余约束；
- 下一轮只围绕剩余不确定性展开。

如果轨迹已经被错误前提污染，则 Restart，不把旧状态继续带入新一轮。

## 最关键的设计：Research State，而不是聊天摘要

长程研究会不断累积：

- 搜索结果；
- 暂定结论；
- 已否定候选；
- 冲突来源；
- 重复观察；
- 已过期计划。

常见 Context Compaction 只在达到 Token 阈值时做摘要。这种做法把上下文管理当成容量问题，容易丢失真正影响下一步决策的信息。

AREX 提供显式的 `update_context` Tool，由模型在研究转折点主动调用。它保留：

```text
已验证发现及来源标识
当前候选
未解决约束
有效性和时间风险
已否定候选及原因
下一步研究计划
```

它删除：

```text
重复观察
已被替代的结论
失效计划
不再影响决策的原始 Tool Output
```

因此，`update_context` 不是普通 Summary，而是一次**研究状态提交**。

## Context Update 的实验证据

论文在 BrowseComp 上分析了 Autonomous Context Updating（ACU）：

- 80.3% 的任务调用过 `update_context`；
- 调用时平均上下文约 25,721 Tokens，中位数约 25,386；
- 只有 0.01% 的更新发生在 128K 上限附近。

这说明模型通常不是因为上下文“装满了”才压缩，而是在语义转折点主动更新。

最常见触发原因：

| 触发原因 | 占比 |
|---|---:|
| 修改搜索策略 | 66.9% |
| 否定候选 | 13.6% |
| 发现新线索 | 7.2% |
| 汇总进展 | 6.4% |
| 验证证据或答案 | 5.3% |

更新后的状态最常保留：

| 状态内容 | 出现占比 |
|---|---:|
| 下一步计划 | 96.4% |
| 未解决约束 | 95.5% |
| 已否定候选 | 81.5% |
| 已验证发现 | 72.1% |

最有价值的信号是：**AREX 优先保存“下一步该做什么”和“哪些条件还没满足”，而不是保存一份面面俱到的会话摘要。**

## 双循环到底贡献了多少

在 BrowseComp 的内部消融实验中：

| 配置 | Accuracy |
|---|---:|
| 无 ACU、无外层循环 | 59.6 |
| 无 ACU、有外层循环 | 69.8 |
| 有 ACU、无外层循环 | 71.4 |
| 完整 AREX | 82.5 |

由此可见：

- 单独加入 ACU：59.6 → 71.4，提升 11.8 个点；
- 在有 ACU 时加入外层循环：71.4 → 82.5，提升 11.1 个点；
- 完整系统相对两者都没有：提升 22.9 个点。

这是论文内部的受控实验，不是第三方复现，但至少说明两个组件不是单纯装饰：

1. 用结构化状态替代完整轨迹；
2. 对低置信结果进行定向新一轮研究。

## Structured Finish：把研究结果变成可验证对象

内层不能只输出自然语言答案，而应通过 `finish` 返回：

```yaml
answer:
evidence:
  - claim_id:
    source_id:
    excerpt_or_fact:
confidence:
unresolved_constraints:
```

AREX 的外层依赖答案级 Confidence 来决定 Accept、Refine 或 Restart。

工程上不能直接照搬模型自报置信度。更可靠的方法是将 Confidence 拆成可计算指标：

```text
Constraint Coverage
× Evidence Support
× Source Authority
× Temporal Validity
× Cross-source Consistency
```

模型可以给出语义判断，但最终决策应由 Harness 聚合确定性和模型指标。

## 训练方法中最值得学习的部分

AREX 不只改了推理 Harness，还专门训练模型掌握长程研究行为。

### 1. 可验证的约束型任务合成

每个训练问题包含一个答案和一组可验证约束。有效任务必须满足：

- 答案不能从问题表面直接猜出；
- 每条约束可以从外部证据验证；
- 多条约束联合后能唯一确定答案；
- 证据真实存在且任务难度足够。

这比随意生成“请研究某主题”更适合训练和评测，因为每个结果都能拆成 Constraint-level Reward。

### 2. Teacher Trajectory 质量控制

作者过滤掉：

- 直接猜答案的轨迹；
- 忽略 Tool Observation 的轨迹；
- 无效 Tool Call；
- 无证据结论；
- 不会根据新证据修正假设的轨迹；
- 最终答案无法从收集证据重建的轨迹。

这说明高质量 Agent 数据的核心不是轨迹长，而是**每次关键转向能被外部证据解释**。

### 3. Key-step Focused Supervision

长轨迹中，大多数步骤只是普通搜索和过渡。真正决定成败的是少数关键步骤：

- 多轮探索后第一次获取决定性证据；
- 明确否定错误候选并改变搜索方向；
- 调用 `update_context` 保存有效进展和下一步计划。

作者保留这些步骤的完整前缀作为条件，但只对关键步骤本身计算训练 Loss，避免普通步骤稀释信号。

消融实验中，把关键步骤回放替换成等预算的随机步骤，BrowseComp 从 82.5 降到 74.1，是训练组件中最大的下降。

### 4. Step-aware Reinforcement Learning

普通 GRPO 将最终奖励近似均匀传播到整条长轨迹。AREX 对验证成功轨迹中的关键步骤增加有限的辅助奖励，同时仍把最终答案正确性作为主奖励。

用标准 GRPO 替换 Step-aware RL 后，BrowseComp 从 82.5 降到 79.4。

这不代表所有中间步骤都应该人工打分，而是说明：**长程 Agent 的信用分配不能只看整条轨迹最终是否成功。**

## 不训练模型也能复用的 Harness 方案

### 1. Constraint Ledger

先把用户需求转成显式约束，而不是直接搜索：

```yaml
constraints:
  - id: c1
    statement: 必须来自官方来源
    status: unresolved
    evidence: []

  - id: c2
    statement: 最近 7 天发布
    status: unresolved
    evidence: []

  - id: c3
    statement: 与 Agent Runtime 直接相关
    status: unresolved
    evidence: []
```

状态至少包括：

```text
unresolved
supported
contradicted
not_verifiable
stale
```

### 2. Evidence Store

证据与答案分开存储：

```yaml
evidence_id:
source_url:
source_type:
published_at:
retrieved_at:
claim_supported:
source_authority:
temporal_validity:
conflicts_with:
```

同一证据可以支持多条约束；同一约束也可以引用多个来源。

### 3. Research State

每次状态提交只保存后续决策需要的内容：

```yaml
verified_findings:
current_candidates:
rejected_candidates:
  - candidate:
    reason:
unresolved_constraints:
conflicts:
next_plan:
search_budget_remaining:
```

不要把原始网页全文和所有搜索结果永久放在 Active Context 中。原始材料留在 Trace/Document Store，通过 ID 回查。

### 4. Inner Loop

```text
选出优先级最高的未解决约束
→ 生成针对性查询
→ 获取证据
→ 更新候选与约束状态
→ 到达语义转折点时提交 Research State
→ 生成暂定答案
```

语义转折点包括：

- 候选被否定；
- 证据冲突被解决；
- 搜索方向改变；
- 完成一个重要子问题；
- 上下文接近硬上限。

### 5. Outer Loop

```python
if all_required_constraints_supported():
    return ACCEPT

if trajectory_has_reusable_evidence():
    objective = build_targeted_objective(unresolved_constraints)
    return REFINE(objective)

return RESTART(original_query)
```

Refine 的输入应是剩余问题，而不是原始问题全文加一句“请继续改进”。

## 对每周技术与岗位报告的直接应用

当前周报任务非常适合使用 AREX 思路。

### 原问题拆成约束

```text
技术信号：
- 最近 7 天
- 一手来源
- 对 Agent 工程有实际价值
- 最多 7 条

岗位信号：
- 当前可申请
- 高阶 Agent 相关
- 原始 JD 可核验
- 不重复岗位簇
```

### 第一轮

广泛搜索并得到候选清单。

### 外层验证

逐条检查：

- 日期是否符合；
- 来源是否一手；
- 是否只是营销新闻；
- 岗位是否仍开放；
- JD 是否真的涉及 Agent Runtime/MCP，而不是泛 AI；
- 是否有足够事实支持个人判断。

### 第二轮

只补：

- 没有官方来源的条目；
- 日期不清楚的岗位；
- 技术含义仍不明确的论文；
- 证据冲突或质量不足的候选。

这比每轮重新全网搜索更稳定，也能显著减少重复信息。

## 推荐评测指标

| 指标 | 含义 |
|---|---|
| Constraint Coverage | 必要约束被证据支持的比例 |
| Evidence Precision | 引用证据是否真正支持对应结论 |
| Source Authority | 一手和权威来源占比 |
| Rejected Candidate Recurrence | 被否定候选再次出现的频率 |
| Duplicate Search Rate | 重复查询和重复访问比例 |
| Targeted Follow-up Ratio | 后续搜索是否针对未解决约束 |
| Unsupported Claim Rate | 无证据结论比例 |
| Cost per Verified Constraint | 每个被验证约束的成本 |

这些指标比“报告长度”和“搜索次数”更接近研究 Agent 的真实质量。

## 适用边界

### 论文层面

- 当前是预印本，尚无独立复现；
- Benchmark 和对比结果依赖统一 Agent Interface、搜索环境与评测设置；
- 每个 Episode 最多允许 300 个内层 Turn 和 5 次外层循环，成本并不低；
- 训练数据包含合成任务和强 Teacher 轨迹，数据质量控制本身投入很大；
- Confidence 是模型生成的，虽然论文展示了区分趋势，但生产中仍需外部校准。

### 工程层面

AREX 更适合：

- 多约束信息检索；
- 尽职调查；
- 技术选型；
- 文献研究；
- 供应商、岗位和产品比较。

不适合直接套用：

- 约束无法明确定义的开放创作；
- 证据本身不可获取或不可验证的任务；
- 低价值、低复杂度的简单问答；
- 对时延极度敏感的实时交互。

## 我的结论

AREX 最值得复用的不是“让 Agent 多想几轮”，而是以下四项机制：

1. **把任务拆成可验证的约束，而不是只维护一个模糊目标。**
2. **把已验证证据、未解决约束和已否定候选保存为 Research State。**
3. **后续研究由剩余不确定性驱动，而不是无方向延长搜索。**
4. **区分 Refine 与 Restart：有价值的轨迹增量修复，被污染的轨迹彻底重启。**

一句话概括：

> **高质量 Research Agent 的核心不是搜索得更多，而是每轮结束后更清楚地知道哪些已经成立、哪些仍未成立，以及下一步只该验证什么。**
