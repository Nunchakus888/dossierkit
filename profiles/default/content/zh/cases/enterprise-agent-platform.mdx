## 这个案例需要证明什么

这个案例用于证明你不是“会调 API 做 Agent demo”，而是能把 Agent 做成企业级系统：可接入真实业务流程、可控权限与副作用、可观测、可回放评测、可灰度发布，并能沉淀为多个业务线复用的平台能力。

后续补项目实践时，重点补真实场景、系统规模、团队角色、上线范围和业务指标。

## 业务场景框架

适合填入这类场景：

- 企业内部知识、客服、销售、财务、运营、研发或供应链流程。
- 需要 Agent 调用多个业务系统，而不是只做问答。
- 需要权限、审计、人工接管和稳定性保障。
- 需要把 POC 变成长期可维护的平台能力。

## 技术架构框架

平台可以拆成六层：

1. Agent Runtime：任务状态、计划执行、重试、超时、人工接管和失败恢复。
2. Tool / MCP / Skills：工具注册、schema 管理、版本控制、权限绑定和调用审计。
3. Context / Memory / RAG：业务上下文、知识召回、长上下文策略和历史状态管理。
4. Security / Permission：身份、租户、数据权限、审批流、敏感操作确认和审计日志。
5. Evaluation / Harness：离线回放集、golden set、过程断言、工具副作用检查和发布门禁。
6. Observability / Cost：trace、日志、指标、模型路由、缓存、延迟和 token 成本分析。

## 关键设计决策

- 工具上线不等于 Agent 可调用，必须拆开工具注册、权限审批和运行时授权。
- 每次任务保留结构化 trace，用于问题定位、评测样本沉淀和后续数据飞轮。
- 发布前不只看最终答案，还要检查中间步骤、工具选择、参数、权限和副作用。
- 高频流程优先平台化，低频流程保留人工协同，避免过度自动化。

## 应补充的真实证据

后续你补项目实践时，建议按这组字段填：

- 业务流程：接入了哪个核心流程，原流程痛点是什么。
- 系统规模：用户量、任务量、工具数量、业务系统数量、模型调用量。
- 个人角色：架构负责人、核心模块 owner、跨团队推进还是团队管理。
- 质量指标：任务成功率、人工接管率、工具误调用率、回放通过率。
- ROI 指标：流程耗时、人效提升、成本下降、客诉/错误率变化。
- 稳定性指标：延迟、失败率、告警、灰度发布和事故复盘。

## 面试表达角度

这个案例的表达重点是：你能从业务流程出发，定义 Agent 平台边界，拆出 runtime、工具、权限、评测、观测和数据反馈闭环，并用上线指标证明它不是一次性 demo。
