## Positioning

This case supports one primary direction: enterprise Agent platform architect. It is not a demo story or a broad AI application narrative. The value is YC ownership over the Agent platform, team engineering standards, and delivery quality.

## Platform Scope

The core platform is a cross-industry AI Agent customer-service SaaS foundation supporting 2k+ tenants, 230k+ users, a recent-month peak of 60k requests/day, and about 7s average response time. Its production boundary covers:

1. Agent Runtime: session-level runtime, complex task handling, termination conditions, concurrency control, async execution, and callback delivery.
2. Tool / MCP / Skills: HTTP Tool, MCP adapter, dynamic Skill load/unload, tool gating, and side-effect planner.
3. RAG / Memory: documents, QA, websites, attachments, products, session memory, and context augmentation.
4. Observability / Cost: correlation_id, events, inspection, token usage, callback payloads, and load-test metrics.
5. Quality Loop: badcases, content gaps, human review, knowledge/Skill/Memory updates, replay evaluation, and release gates.

## Architecture Evolution

Agent 1.0 started with a controlled runtime. Guideline, Journey, and ARQ constrained LLM behavior inside a deterministic business execution framework, prioritizing explainability, traceability, and reviewability in real customer-service workflows.

Agent 2.0 evolved into a model-driven runtime. The LLM moved to the center of tool calling and multi-step decisions, while the runtime owned context, action space, dynamic Skill loading, RAG/Memory, tool boundaries, concurrency, and cost governance.

The important signal is not API usage. It is platform abstraction, architecture tradeoff, and system governance under production constraints.

## Team Harness

At the team level, YC has a product-engineering team of about 20 people. I owned the AI Agent business track and led a 3-person squad of 2 developers and 1 QA. I drove AI development harness adoption across 40 repositories so AI-assisted engineering became part of a controlled delivery process. The core model has three layers:

1. Outer Loop: architecture rules, language profiles, layering boundaries, naming, error handling, logging, and observability expectations.
2. Inner Loop: Spec / EPIC workflow for non-trivial changes, including goals, non-goals, acceptance criteria, phases, tasks, and status.
3. Supervisor Gate: change summary, changed files, self-check result, AI Harness trace, and acceptance checklist as delivery gates.

This reduces four common failure modes: architecture drift, runaway refactors, inconsistent quality, and acceptance gaps. For senior positioning, it shows not only individual delivery ability, but also the ability to turn AI-assisted development and team collaboration into a repeatable engineering process.

## Stack

The main stack includes Python, TypeScript, Rust, Java, FastAPI, Milvus, Alibaba Cloud, Google Cloud, and Gemini. The stack is supporting evidence for platform complexity and engineering breadth; the main story remains Agent Runtime, tooling, RAG/Memory, evaluation gates, observability, and team engineering governance.
